# Datasheet for LLM-VulnGen

Following Gebru et al., "Datasheets for Datasets" (Communications of the ACM,
2021). Answers are intentionally concise; see the accompanying paper for detail.

## Motivation

**For what purpose was the dataset created?**
To measure and analyze how often, and under what conditions, contemporary LLMs
generate insecure web application code, and to provide a reusable benchmark for
training and evaluating vulnerability detectors.

**Who created the dataset and who funded it?**
The authors (Center for Applied Computing, University of Oulu). Funding details
are stated in the paper's acknowledgments.

## Composition

**What do the instances represent?**
Each instance is a single LLM-generated source-code sample for a web
development task, plus metadata and automatically detected security labels.

**How many instances are there?**
1,080.

**Does the dataset contain all possible instances or a sample?**
It is a controlled sample produced by a factorial design: 4 models × 30
(task, strategy) prompts × 3 temperatures × 3 generations.

**What data does each instance consist of?**
The generated code (raw text) and metadata: model, task, language, prompt
strategy, temperature, detected vulnerability types, per-type confidence
scores, and derived fields. See `docs/SCHEMA.md`.

**Is there a label or target associated with each instance?**
Yes. Each sample carries a binary `is_vulnerable` label and a list of detected
vulnerability types with confidence scores.

**Is any information missing?**
No personal or sensitive attributes are included. The dataset contains no
ground-truth from external auditors beyond the manual validation described in
the paper.

**Are there errors, sources of noise, or redundancies?**
Labels come from a pattern-matching detector and may miss complex or
context-dependent vulnerabilities (limited recall). A manual review of a
stratified sample of 50 instances found no false positives among high-confidence
detections. Multiple samples may be near-duplicates because three generations
were drawn per configuration.

**Does the dataset contain confidential or personal data?**
No. It contains synthetic code generated by models; no human-subject data.

**Could the dataset be offensive or harmful?**
It contains deliberately insecure code. It does not contain working exploits,
malware, or instructions for attacking specific systems. See the ethics section
of the README.

## Collection process

**How was the data collected?**
Prompts were programmatically constructed by crossing web tasks with
vulnerability-inducing strategies. Each prompt was sent to four locally run
LLMs at three temperatures, sampling three generations each.

**Over what time frame?**
Generation timestamps are recorded per sample (`timestamp` field); see paper.

**Were any ethical review processes conducted?**
No human subjects were involved, so IRB review was not required. The dual-use
considerations are discussed in the paper and README.

## Preprocessing / labeling

**Was any preprocessing/cleaning/labeling done?**
Generated outputs were stored verbatim. Vulnerability labels were produced by an
automated detector using regular-expression patterns with confidence scoring.

**Was the raw data saved?**
Yes. The raw generated code is preserved in the `code` field.

## Uses

**Has the dataset been used already?**
Yes, for the analysis reported in the accompanying paper.

**What tasks could the dataset be used for?**
Training/evaluating vulnerability detectors; benchmarking model security;
studying prompt-to-vulnerability relationships; education.

**Is there anything that should be avoided?**
Do not deploy samples in production or use the dataset to attack real systems.

## Distribution

**How is the dataset distributed?**
Through a public Git repository and an archival service (Zenodo) that mints a
persistent DOI.

**Under what license?**
Data: CC BY 4.0. Accompanying code: MIT.

## Maintenance

**Who maintains the dataset and how can they be contacted?**
The corresponding author (see `CITATION.cff` and the paper). Issues and
contributions are accepted through the repository's issue tracker.

**Will the dataset be updated?**
Planned extensions include additional models, languages, tasks, and vulnerability
types. Versioned releases will receive distinct DOIs.
